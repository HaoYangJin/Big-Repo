# Git 仓库工作流

以下是本仓库的协作约定，可按其他项目的实际需求调整。

## 开始修改

查看 git status、当前分支和已有差异，保留与任务无关的工作。
默认分支使用 main；功能修改建议使用 feat/简短名称、修复使用 fix/简短名称、文档使用 docs/简短名称。
初始化空仓库时可以直接建立 main 的首个提交。

## 组织提交

一次提交围绕一个可解释的目标。用 git add -- 文件路径 精确暂存，必要时使用 git add -p。
提交前查看 git diff --cached 和 git diff --cached --check，确认没有凭据、临时输出或无关文件。
提交信息遵循 [提交规范](../skills/git-commit/references/commit-conventions.md)。

## 验证

根据改动执行实际需要的检查：文档查看内容和链接，代码执行相关测试，脚本运行代表性输入。
失败时说明失败原因与影响，不能把未运行的检查标为通过。

## 推送与 PR

推送前确认远端、分支和待推送提交，按用户授权范围操作。
PR 描述解释解决的问题、最终行为、验证证据与必要的迁移说明，可使用仓库的 PR 模板。
不要自动推送其他人的提交、强制推送、删除远端分支或重写共享历史；确需此类操作时先确认授权。
发生冲突时保留双方意图并重新验证。合并方式按目标仓库设置执行，不在本规范中强制指定。

## 本仓库的 AI 自动交付

在当前维护任务中默认自动诊断和修复范围内失败，使用独立 AI 子代理或独立会话审查最终候选；实现者自评不能替代独立审查。修复审查发现后重新验证和复审，不通过就不合并。
通过本地检查、独立审查与最终提交的全部登记 CI 后，使用插件 `merge` 命令重新检查门槛，带 `--match-head-commit` 执行默认 squash，并查询 PR 确认 MERGED 与合并提交；不使用 `--admin`、强推或自动删除分支。
等待中的检查只读等待；结果不确定的写操作先查询远端，不盲目重试。项目要求的人工审批与平台保护不能用 AI 审查记录替代。用户限定只本地、只审查或只交付 PR 时遵守限定。
用户已明确要求发布具体版本时，单独记录该版本、合并提交及制品范围后在同一委托中发布并核验，不重复确认已有授权；默认维护不包含发布、部署或全局安装。
