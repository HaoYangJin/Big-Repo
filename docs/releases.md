# 获授权的插件发行

维护任务默认只准备材料。用户明确要求发布具体版本后，先完成维护 PR 的独立审查、本地验证与 CI 并确认合并，再固定标签和已验证插件 ZIP 的 SHA-256。不得移动已有标签或覆盖不同字节的已发行制品。

正常云认证可以操作 GitHub API，但某些环境的凭据未覆盖 `uploads.github.com`。本仓库提供手动触发的 `Release plugin` 工作流，使用仓库自己的临时 `GITHUB_TOKEN` 上传；不保存个人令牌，不修改云代理的凭据，不建立定时任务。

## 准备与执行

1. 从已合并提交运行完整测试、两次打包并逐字节比较，核对双平台清单版本、ZIP 完整性与 SHA-256。
2. 创建并推送固定于该提交的 `vMAJOR.MINOR.PATCH` 标签，创建相同标签的 GitHub Release **草稿**并填写真实说明。草稿必须已存在；脚本不自行创建发行或标签。
3. 在默认分支的 Actions 中手动运行 `Release plugin`，输入 `tag`、完整 `commit` 和本地已验证 ZIP 的 `sha256`。此操作会公开指定发行，应属于用户已授权的版本发布任务。
4. 工作流从指定标签重新运行实际测试和两次构建，要求源提交、插件版本、构建摘要与输入一致；随后上传 ZIP、SHA-256 及从标签内安装文档生成的 `INSTALL-版本.md`。
5. 上传后下载草稿资产逐个核验，再次核对远端标签，随后公开并设为 Latest，最后下载公开资产复核。只有实际公开和字节一致才报告完成。

2.0.0 起安装说明由该标签内的 docs/install.md 生成，引用固定版本迁移和工作流资料；1.x 保持使用标签内的插件 README。内容包括校验、升级和回退流程。构建与测试阶段不注入上传令牌；上传步骤仅使用仓库范围的 `contents: write` 权限，不绕过组织、环境或平台规则。

## 中断与恢复

工作流按版本串行，不取消正在进行的发行。不使用 `--clobber`，不覆盖、删除资产或移动标签。已有同名资产只有下载后字节相同才复用；出现额外资产、上传未完成、不同字节、标签改变、零测试或摘要不符时停止。

写入超时或失败后先检查远端状态，再决定是否重新触发。新运行会重新验证当前草稿与已有资产，不盲目重试旧写入；若发行已经公开，只有完整资产都匹配才确认完成，不再写入。撤回或替换已公开版本需单独判断影响和授权，不能以移动标签修复。

本工作流使用默认分支的发布脚本、标签中的已审查源码。两者可以来自不同提交，发行制品始终以输入中固定的源码提交及摘要为准，不把后续发布基础设施提交冒充标签内容。
