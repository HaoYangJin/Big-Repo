# 1.1.0：AI 自动修复与合并

## 本轮问题与变更

1.0.0 已声明默认自动合并，但首次非预期失败就交接，工具只观察合并门槛，实际合并与确认仍依赖调用方临时拼接操作。本轮用户明确要求维护自动化，并授权迭代后发布 1.1.0。

- 六项技能统一为范围内诊断、修复、验证、独立 AI 审查与复审，完成 CI 后自动合并。只在外部阻塞或范围内无法解决的问题出现时交接。
- 新增 `repo_tools.py merge`，复用全部本地、审查、权限及 CI 门槛，再执行一次带 `--match-head-commit` 的 squash 合并；重新查询 PR，确认 MERGED、原 head、仓库/分支及有效合并提交后才报告成功。
- CI 尚待完成返回 waiting；跳过、取消或失败仍阻止合并。写入超时、进入合并队列、远端查询失败或身份不匹配均不当作已合并；先读取远端状态，禁止盲目重复写入。
- 历史失败按候选版本保留日志，当前证据只记录最终候选的真实验证，不用旧失败永久阻止修复后的候选，也不声称历史上没有失败。
- 维护任务的 commit/push/create-pr/merge 授权格式不变。明确要求发布具体版本可在同一委托内另记发布范围，维护 PR 合并后继续发布；默认仍只准备材料。
- 同步双平台插件清单、市场版本、安装入口、升级说明、代理规则、贡献说明及任务/交接模板。
- 实际远端门槛检查发现 GitHub CLI 2.46 拒绝旧查询中的 `baseRefOid` 字段，导致所有 PR 查询失败；移除该未使用字段并补充回归检查，保留必要的 head、目标分支及合并提交核对。

此处的自动化指当前用户委托的端到端交付，不增加常驻服务、定时任务、全局安装、部署或对其他仓库的权限。项目要求的人工审批与平台保护继续生效。

## 验证范围与记录

当前云环境为 Linux、Python 3.12.14 和 Git 2.52.0，仅使用 Python 标准库。修改前基线为 72 项测试全部通过。新增 9 项合并执行回归测试，覆盖：

- 所有门槛通过后仅执行一次锁定 SHA 的 squash，且本地工作区不变。
- 等待或失败 CI、旧证据、旧审查、缺失授权和远端 head 变化时不写远端。
- 合并排队、提交或身份不匹配、缺少有效合并提交时不误报成功。
- 写入命令失败后读取远端实际结果；超时与查询失败保留不确定状态，不重复合并或泄露错误内容。
- CLI 的合并分派、必需参数和 0/2/3 退出码。

这些测试使用临时 Git 仓库和隔离 GitHub 响应，不宣称实际远端合并成功。首次完整运行的 81 项测试有 1 项失败：README 已引用尚未创建的本记录，Markdown 链接检查准确发现缺失；通过补齐记录修复，未删断言或跳过检查。修复后 81 项全部通过，失败 0、跳过 0。随后真实远端检查暴露上述 CLI 字段兼容问题，修复后重新验证和独立审查，最终结果以最终提交的运行证据为准。

可复现命令：

```text
python -m unittest discover -s tests
git diff --check
python scripts/build_plugin.py --output dist
```

本轮还完成双次构建逐字节比较、SHA-256 与 ZIP 完整性核验、双平台版本一致和六技能清点；从解压后的包运行 snapshot 成功，缺失任务与证据的 merge 被拒绝。研究数据未更新，使用现有快照在仓库外临时目录成功重建 60 份档案，不覆盖受跟踪研究文件。合并后的发行仍需从实际合并提交重新构建和验证。

1.0.0 的 Codex/Claude Code 加载和模型冒烟记录保留在 [验收报告](../validation.md)，不能代替本版客户端端到端验证。本轮不修改全局插件配置。

## 合并与发行

用户已明确授权本仓库 1.1.0 的标签、GitHub Release、插件 ZIP、SHA-256 和安装说明上传。先通过独立审查、本地验证与最终 PR head 的三系统 CI，运行 merge 工具确认合并，再从合并提交构建并创建发行草稿、上传制品、核验后公开；最后下载已发布制品复核。不能从本记录或已更新的版本入口推断实际发行已完成。

网络与权限、PR/CI、合并提交及实际发行状态均需实时查询；不可把旧版本的 CI 或只读 Git 成功当作本次权限证明。若环境阻止远端操作，保留本地改进、验证、任务及证据，明确交接精确所需的访问配置。

## 迁移与回退

任务和证据 JSON 与 1.0.0 兼容；`merge` 为新增写命令，`merge-readiness` 仍只读。默认首次失败停止改为有诊断的自动修复；需要旧策略时在任务中明确要求首次非预期失败就交接。

升级采用完整 1.1.0 插件目录，不混合覆盖文件。回退时停用新版并重新指向 1.0.0 目录或固定标签，保留项目规则和用户改动；不要移动发行标签或用另一套字节覆盖已发布制品。
